# Секреты и конфигурация (Ф12)

Вся настройка — переменные окружения, читаются и проверяются в `src/config.ts`. В коде и репозитории ключей нет (сторож в `test/config.test.ts` проверяет `src/`). Список имён — `.env.example` (только имена, без значений).

## Переменные

| Имя | Обяз. в prod | Что это |
|---|---|---|
| `LUMO_MODE` | нет (по умолч. **prod**) | `prod` / `dev` / `test` |
| `SESSION_SECRET` | **да** | серверный секрет: им «подсаливается» хеш токена сессии в базе (HMAC-SHA256) |
| `DATABASE_PATH` | **да** | файл базы SQLite; `:memory:` в prod запрещён |
| `COOKIE_SECURE` | **да** (=`1`) | кука сессии с `Secure` (сервер стоит за HTTPS) |
| `TRUSTED_PROXY` | за прокси — да | адреса прокси через запятую; только от них верим `X-Forwarded-For` (иначе у всех клиентов один адрес). Пусто — заголовок игнорируется |
| `BACKUP_DIR`, `BACKUP_KEEP` | для бэкапа | каталог копий, сколько хранить (1–3650, по умолч. 14) |
| `PORT` | нет | по умолч. 8787, слушает только 127.0.0.1 |
| `RETENTION_MESSAGE_DAYS`, `RETENTION_LOGIN_ATTEMPT_DAYS` | нет | сроки хранения для `npm run maintenance` |

Правила `SESSION_SECRET` в prod: не короче 32 символов, не меньше 8 разных символов, без пробелов, без слов-заглушек (`changeme`, `secret`, `test`, `password` и т. п.). Иначе сервер **не стартует**; в ошибке — имя переменной и причина, значение не печатается. В `dev`/`test` без секрета генерируется случайный на процесс (после перезапуска сессии сбрасываются).

`npm run seed` в prod отказывается (у демо-пользователей известные пароли); для локального демо — `LUMO_MODE=dev`.

## Как задать на сервере

1. Сгенерировать: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` — вывод сразу в файл, не в чат и не в историю команд.
2. Положить в файл окружения вне репозитория, например `/etc/lumo/env` (владелец — пользователь сервиса, права `0600`), строки вида `ИМЯ=значение`.
3. Запускать процесс с этим окружением (например, `EnvironmentFile=` в unit-файле systemd или `set -a; . /etc/lumo/env; set +a`).
4. Проверка: запуск без `SESSION_SECRET` должен завершиться ошибкой `config error: SESSION_SECRET is required…`.

## Ротация

Плановая (например, раз в год) или после любой смены людей с доступом: сгенерировать новый секрет, заменить в файле окружения, перезапустить сервер. Эффект: **все текущие сессии перестают действовать**, пользователи входят заново. Пароли пользователей хранятся отдельно (scrypt с индивидуальной солью) и от `SESSION_SECRET` не зависят.

## Если секрет утёк

1. Немедленно ротировать `SESSION_SECRET` (см. выше) и перезапустить сервер — старые токены перестают работать.
2. Если могла утечь копия базы или бэкап — это данные детей: сообщить владельцу школы, оценить обязанность уведомления; пароли пользователей сбросить.
3. Если ключ попал в git: удаления коммитом недостаточно — считать скомпрометированным, ротировать; историю чистить отдельным решением владельца.
4. Записать, когда и как случилось, и что сделано.

## Перед коммитом

`bash tools/secret_check.sh` после `git add` (хук pre-commit его запускает); `.env*` (кроме `.env.example`), `*.db`, `*.sqlite`, `*.pem`, `*.key`, `backups/`, `*.log` в `.gitignore`.
