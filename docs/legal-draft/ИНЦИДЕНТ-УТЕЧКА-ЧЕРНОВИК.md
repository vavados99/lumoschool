# Действия при утечке или подозрении на утечку (черновик)

Сроки отмечены «проверит юрист» — я их не утверждаю. В RODO есть общее требование уведомлять надзорный орган и, при высоком риске, людей; точные сроки, форму, адресата (в Польше — национальный орган по защите данных) и статьи подтверждает юрист.

## Что считается инцидентом
Подозрение на: чужой доступ к базе/копиям/серверу; утечку `SESSION_SECRET` или паролей; показ данных не тому человеку (дыра изоляции ролей); потерю носителя; письмо не тому адресату; публикацию данных детей.

## Порядок
1. **Обнаружение (сразу).** Кто заметил → Влад. Записать время обнаружения (от него может идти отсчёт сроков — *проверит юрист*).
2. **Остановить (сразу, тех.).** Выключить сервер/доступ; при подозрении на секрет — сменить `SESSION_SECRET` (`docs/SECRETS.md`, все сессии сбросятся) и пароли; до снимка ничего не стирать (копия БД — `npm run backup`, права 0600).
3. **Собрать факты (тех.).** `audit_log` (`GET /api/owner/audit`: кто, действие, цель, исход, время; текстов нет; **хранится 365 дн.** — более ранние события уже удалены чисткой, а у стёртых по просьбе людей actor/target = 0), журнал сервера, список затронутых людей (`users`, `parent_child`), какие поля (контакты? сообщения детей?). База на диске **не шифруется**. Удалённое по просьбе остаётся в копиях до ротации (14 копий по умолчанию).
4. **Оценить риск (Влад + юрист).** Затронуты ли дети, контакты, переписка; вероятность вреда.
5. **Уведомить надзорный орган.** Срок — *проверит юрист*. Содержание: что, сколько людей, последствия, меры.
6. **Уведомить родителей/людей** при высоком риске. Срок — *проверит юрист*. Каналы: очередь `notification_outbox` (реальный отправитель не подключён — только по «да» Влада) или вручную по контактам из `contact_vault` (`GET /api/contacts/:id`, только владелец); язык — `users.lang` (uk/pl/en/de/cs/ru). Шаблонов писем нет.
7. **Закрыть.** Причина, исправление (тест, повторяющий дыру — как в Ф17–Ф23), запись в реестр инцидентов [формы нет — завести], пересмотр `ДАННЫЕ-РЕЕСТР.md`.
8. Реестр инцидентов ведётся и без уведомления органа (*обязательность — проверит юрист*).

## Чего в коде нет
Мониторинга и оповещений нет (планировщик пишет в журнал только сбои, `GET /api/owner/scheduler` — в памяти); автодетекции аномалий нет, только лимиты входа и частоты (`f5-auth.test.ts`, `f17-gates.test.ts:83`, `f19-ratelimit.test.ts`); сервера в ЕС и договора с хостингом нет.

## Канал приёма просьб об удалении / доступе / отзыве
- **Работает в коде:** родитель и ученик 16+ сами экспортируют данные (`GET /api/export/:id`) и отзывают согласие (`POST /api/consents/:id/revoke`). Экрана нет — только API.
- **Удаление работает в коде (Ф25/Ф26):** `POST /api/erase/:id` с `{"confirm":true}` (необратимо). Владелец — любого ученика или родителя; родитель — себя или своего ребёнка до 18; ученик (в т. ч. 16+) и преподаватель — 403; преподавателя и владельца стереть нельзя; чужого ребёнка — 403. Ядро — `eraseData` (`data.erase`/`data.erase_any`). Экрана нет — только API; запрос на удаление выполняет владелец или родитель сам.
- **Приём:** адрес/форма — [не заданы, решает Влад]. Предложение: один адрес для данных на домене школы; ответ в срок, который назовёт юрист; перед удалением обязательна проверка личности просящего (по `parent_child` и контакту в сейфе) — в коде её нет; просьба и исполнение записываются в реестр (в `audit_log` попадает только `data.erased`, не сама просьба).
- **Что остаётся после удаления:** согласия и записи об уроках без имени — до +6 лет (предположение); `audit_log` — строки остаются, ссылки на человека заменены на 0, итоговая строка `data.erased` хранит id (ей действует тот же срок журнала 365 дн.); «надгробие» `erased_subjects` (только id и время, без срока); копии и файлы `*.pre-restore-*` — до ручного удаления/ротации (14); при `npm run restore` стёртые обезличиваются повторно (`restore.ts`; если рабочая база нечитаема — предупреждение, просьбы повторить вручную); старая копия, восстановленная в НОВЫЙ путь, о стёртых не знает. Чат комнаты: реплики стёртого человека удаляются, реплики других остаются; `room_presence` уходит после срока хранения записей об уроках.
