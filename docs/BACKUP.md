# Резервные копии базы и восстановление (Ф11)

База — один файл SQLite (`DATABASE_PATH`). В ней **данные детей и родителей**: имена, даты рождения, контакты, согласия, переписка, журнал. Копия содержит всё это же, поэтому защищать её надо так же строго, как саму базу.

## Сделать копию

```sh
cd платформа
DATABASE_PATH=/var/lib/lumo/lumo.sqlite BACKUP_DIR=/var/backups/lumo npm run backup
# → backup ok: /var/backups/lumo/lumo-backup-20261018T013005123Z.sqlite
```

- Копия снимается средствами SQLite (`VACUUM INTO`): это целостный снимок, **сервер можно не останавливать**. Просто `cp lumo.sqlite …` делать нельзя — можно скопировать половину записи.
- После снятия копия проверяется (`PRAGMA integrity_check`); если проверка не прошла, файл не появляется.
- Имя: `lumo-backup-<дата-время UTC>.sqlite`. Права на файл `0600`, на каталог `0700`.
- Ротация: хранятся `BACKUP_KEEP` последних копий (по умолчанию 14), остальные удаляются. Удаляются **только** обычные файлы с именем ровно такого шаблона прямо в `BACKUP_DIR`; всё прочее (другие файлы, ссылки, подкаталоги) не трогается — поэтому не кладите в `BACKUP_DIR` ничего нужного под именами `lumo-backup-*.sqlite`.
- Если база занята долгой записью, копия ждёт до 10 секунд, потом сообщает об ошибке (код выхода 1) — ночью это не должно случаться.

## Восстановить

1. **Остановите сервер** (иначе он будет писать в подменяемый файл).
2. Выберите копию (последняя — с самой поздней датой в имени) и запустите:

```sh
DATABASE_PATH=/var/lib/lumo/lumo.sqlite npm run restore -- /var/backups/lumo/lumo-backup-20261018T013005123Z.sqlite
# → restore ok: /var/lib/lumo/lumo.sqlite
# → previous database kept as: /var/lib/lumo/lumo.sqlite.pre-restore-20261018T090000000Z
```

3. Запустите сервер и проверьте вход и данные.

Что делает `restore`:
- **До** любых изменений проверяет копию: `integrity_check`, `foreign_key_check`, `user_version` (не 0 и не новее, чем знает код), наличие всех нужных таблиц. Битая или чужая копия отвергается (`restore FAILED: backup rejected: …`), рабочая база не тронута.
- Рабочую базу молча не затирает: прежний файл (даже повреждённый) сохраняется рядом как `<база>.pre-restore-<время UTC>` с правами `0600`. Когда убедитесь, что всё хорошо, страховку удалите вручную — она тоже содержит данные детей.
- Убирает хвосты старой базы (`-wal`, `-shm`, `-journal`), чтобы они не испортили восстановленную.
- Копия старой схемы дополнится нужными миграциями при первом запуске сервера.

**Откат восстановления:** `npm run restore -- <файл .pre-restore-…>`.

Данные, появившиеся после момента копии (до 24 часов при ночном расписании), при восстановлении теряются — это цена суточного бэкапа.

## Встроенный планировщик (Ф19c)

Реальный сервер (`npm start`) сам запускает по таймерам: `processOutbox`, чистку (срок хранения + сессии + попытки входа, как `npm run maintenance`) и копию с ротацией. В тестах и `seed` не запускается.

| Переменная | Умолчание | Нижняя граница | Смысл |
|---|---|---|---|
| `SCHEDULER` | `on` | — | `off` — выключить планировщик полностью |
| `SCHEDULER_BACKUP_MS` | 86400000 (сутки) | 60 с | период копии; копия делается только если задан `BACKUP_DIR` |
| `SCHEDULER_CLEANUP_MS` | 3600000 (час) | 60 с | период чистки |
| `SCHEDULER_OUTBOX_MS` | 60000 (минута) | 5 с | период `processOutbox` |

- Значение ниже границы поднимается до границы; `0` и не-числа — ошибка конфигурации.
- Копия идёт по таймеру **после старта + интервал** (не сразу при запуске): при частых перезапусках короче интервала копий не будет — используйте `npm run backup` вручную или cron.
- Не запускается наложение той же задачи: если прошлый запуск не закончен, пропуск пишется в `audit_log` (`scheduler.<задача>.skipped_overlap`); сбой — `scheduler.<задача>.failed` (только имя задачи, без текста ошибки). Остальные задачи и сервер продолжают работать.
- Outbox: вне `LUMO_MODE=prod` — консольный сток; в prod без реального канала задача не запускается (очередь ждёт). Реальной отправки нет.
- Если вы настроили внешний cron из раздела ниже — отключите один из двух путей (`SCHEDULER=off`) или уберите `BACKUP_DIR` у сервера, чтобы не делать копии дважды.

**Ф21: «живость» и остановка.**
- Последний успешный тик каждой задачи (`outbox`, `cleanup`, `backup`) хранится в памяти процесса и отдаётся только владельцу: `GET /api/owner/scheduler` → `{enabled, tasks:{<имя>:{intervalMs, lastOkAt, lastEvent, lastEventAt, okCount, failCount}}}`. Только время и счётчики: ни данных пользователей, ни текста ошибок. В `audit_log` успешные тики по-прежнему не пишутся. `lastOkAt: null` у `backup` дольше интервала + запас — копии не делаются, смотреть здесь, а не ждать жалоб.
- **Слабо:** память процесса — после перезапуска всё `null` до первого тика (копия идёт «после старта + интервал»); внешнего оповещения нет — владелец должен сам заглянуть в ручку.
- Остановка (SIGTERM/SIGINT): новые соединения не принимаются, запросы в полёте дожидаются до `SHUTDOWN_TIMEOUT_MS` (умолчание 10000, 100–600000), потом оставшиеся рвутся, затем закрывается база. Копия, начатая планировщиком, остановку не задерживает: таймеры гасятся, а выполняемая синхронно `backupDb` блокирует цикл событий и до конца дорабатывает сама.

## Ночное расписание через cron (пример, на сервере НЕ настроено; альтернатива планировщику)

Расписание задаёт внешний планировщик (cron, systemd timer): в ядре приложения его нет. Пример строки для `crontab` служебного пользователя, например в 03:15:

```cron
15 3 * * * cd /opt/lumo/платформа && /opt/lumo/nightly.sh >> /var/log/lumo-nightly.log 2>&1
```

Содержимое `nightly.sh` (создайте на сервере сами; в репозитории его нет):

```sh
#!/bin/sh
set -eu
export DATABASE_PATH=/var/lib/lumo/lumo.sqlite BACKUP_DIR=/var/backups/lumo
umask 077
# 1. чистка по сроку хранения (сообщения, попытки входа, истёкшие согласия) и просроченных сессий
cd /opt/lumo/платформа
npm run --silent maintenance      # src/maintenance.ts: runRetention от имени владельца + purgeExpiredSessions + purgeOldAttempts
# 2. копия — ПОСЛЕ чистки, чтобы в копии не лежало то, что уже положено удалить
npm run --silent backup
# 3. вынос копии в отдельное место (см. ниже) — например rsync/rclone в хранилище ЕС
```

Порядок важен: сначала чистка, потом копия. Следите за кодом возврата и логом: молчащий планировщик — главный риск.

Важно про сроки хранения: удалённые по сроку данные остаются в **старых копиях** до их ротации (14 дней по умолчанию). Если человек потребовал удаления, а потом вы восстановили копию — он вернулся бы в базу. Поэтому с Ф26:

- При стирании (`POST /api/erase/:id`) в таблицу `erased_subjects` пишется «надгробие»: **только id и время**, без имён, контактов и текстов. Таблица только дописывается (триггеры запрещают правку и удаление).
- `npm run restore` **до подмены** рабочего файла переносит надгробия из рабочей базы в восстановленную и повторно обезличивает этих людей тем же кодом, что и обычное стирание. В журнале остаётся `data.reerased_after_restore`; в консоли — `re-erased after restore: N`.
- **Восстанавливайте поверх рабочего пути** (`DATABASE_PATH`): надгробия берутся из рабочей базы. Копия, сделанная после стирания, несёт надгробие сама. Старая копия, восстановленная в **новый** путь, о стёртых не узнает — это ограничение.
- Если рабочая база нечитаема (повреждена), надгробия взять неоткуда: `restore` печатает `WARNING … Repeat every erasure request received since the backup date`, пишет в журнал `restore.tombstones_unreadable` — **повторите вручную все просьбы об удалении, полученные после даты копии** (список — у вас, он не хранится в коде).
- Копии, которые вы вынесли за пределы `BACKUP_DIR`, и страховка `*.pre-restore-*` содержат данные стёртых людей до удаления файла вручную. Срок копий — ротация 14 дней (`BACKUP_KEEP`); страховку удалите, как убедитесь, что всё хорошо.
- Тест: `test/f26-erasure-layers.test.ts` (seed → копия → стирание → restore из старой копии → субъект обезличен, остальные данные совпадают с копией).

## Где хранить копию

- **Не на том же диске и не на том же сервере**, что и база: иначе поломка сервера уносит и то и другое. Нужно отдельное место.
- Хранилище и сервер — **в ЕС** (данные детей; GDPR).
- Доступ только у владельца и администратора; копия на диске шифруется (шифрование диска или шифрованное хранилище). Файлы копий — `0600`, никому не отправляйте их по почте и в мессенджерах и не кладите в репозиторий (`backups/`, `*.bak` исключены в `.gitignore`).
- Раз в квартал проверяйте восстановление на деле: восстановите последнюю копию во **временный** файл (`DATABASE_PATH=/tmp/check.sqlite npm run restore -- …`), запустите на нём сервер или сделайте выборку и удалите файл. Копия, которую не пробовали восстановить, — не копия.

## Что не покрывается

- Копия не проверяет, что содержимое «правильное»: она ловит структурные повреждения файла, но не подмену значений внутри текстовых полей. Для этого храните контрольные суммы рядом, если нужно.
- Копирование в удалённое хранилище и шифрование — за пределами этих скриптов.
